# خطة تحسين سرعة تحميل الموقع — Key2lix

هذا المستند يلخص **أسباب البطء** و**خطط تنفيذ احترافية** قابلة للتطبيق بالترتيب (أولوية وجهد/مردود).

---

## ما تم تنفيذه (تقليل ثقل التحميل الأولي)

| الإجراء | الصفحات | التأثير |
|---------|---------|---------|
| **Preload لـ style.css** | الرئيسية، تسجيل الدخول، المنتجات | المتصفح يبدأ تحميل الـ CSS الحرج فوراً دون انتظار. |
| **تحميل Font Awesome بدون حجب العرض** | نفس الصفحات | `media="print"` ثم `onload="this.media='all'"` — الأيقونات لا تؤخر أول رسم للصفحة. |
| **تحميل home.css بدون حجب** (الرئيسية فقط) | index.html | نفس التقنية؛ المحتوى المرئي يظهر أسرع. |
| **defer لجميع السكربتات** (الرئيسية) | index.html | تحميل وتنفيذ السكربتات بعد انتهاء تحليل الـ HTML؛ أول رسم أسرع. تم لفّ السكربت المضمن في `window.__key2lixHomeReady` واستدعاؤه عند `DOMContentLoaded`. |

**تطبيق النمط على صفحات أخرى:** أضف في `<head>` لكل صفحة:
- `<link rel="preload" href="/assets/css/style.css" as="style">` قبل رابط الـ style.
- لـ Font Awesome: `media="print" onload="this.media='all'"` مع `<noscript>` fallback.

## تحليل الأرقام التي أرسلتها

| النوع | أمثلة | ملاحظة |
|-------|--------|--------|
| **صفحة رئيسية** | GET / → 312ms ثم 2s | تذبذب كبير (احتمال cold start) |
| **CSS/JS** | home.css 157ms، wishlist.js 290ms، **search.js 8s**، **common.js 16s** | بعض الملفات بطيئة جداً |
| **صور** | **Subscriptions.jpg 15s**، **Promo Banner.png 23s**، Hardware.jpg 23s، Game Cards.png 23s، PayPal.png 20s | تأخير شديد — حجم كبير و/أو cold start |
| **API** | /api/config، /api/client/me → 200–300ms، أحياناً 304 | مقبول لكن **مكرر عدة مرات** في نفس الصفحة |
| **طلبات مشبوهة** | /wp-admin/setup-config.php → 404 | بوتات؛ الرد 404 سريع مناسب |

**الاستنتاج:** البطء الشديد (8–23 ثانية) يأتي من: **(1)** استيقاظ الخدمة من النوم على Railway، **(2)** صور ثقيلة بدون تحسين أو CDN، **(3)** طلبات API مكررة، **(4)** أصول ثابتة تمر بكل الـ middleware قبل `express.static`.

## الخطة 1: تقديم الأصول الثابتة مبكراً (أولوية عالية — جهد قليل)

**المشكلة:** طلبات `/assets/*` تمر عبر الجلسة، rate limit، CORS، admin security، ثم تصل إلى `express.static` في منتصف الملف. أي طلب أصول يدفع تكلفة كل هذا المسار.

**الإجراء:**
- تركيب **`express.static` لمجلد الأصول** (`/assets`) **قبل** middleware الجلسة وكل مسارات الـ API.
- الإبقاء على مسار الـ static الحالي للصفحات وملفات أخرى إن لزم، أو توحيد التقديم تحت `/assets` فقط في المسار المبكر.

**النتيجة المتوقعة:** استجابة أسرع لـ `/assets/css/*`, `/assets/js/*`, `/assets/img/*` وتقليل استهلاك CPU ووقت الاستجابة.

**الملف:** `server.js` — إضافة استخدام لـ `express.static` خاص بـ `client/assets` (أو `CLIENT_ROOT + '/assets'`) بعد `registerStatic` وقبل `app.get('/')` وmiddleware الجلسة، مع نفس الخيارات (maxAge, etag, setHeaders لـ Cache-Control).

---

## الخطة 2: تخفيف نوم الخدمة (Cold Start) على Railway (أولوية عالية — جهد قليل)

**المشكلة:** أول طلب بعد فترة خمول يدفع "استيقاظ" الحاوية → 8–23 ثانية.

**الإجراء:**
- استخدام **UptimeRobot** (أو خدمة مشابهة) لطرق **GET /ping** كل **5–10 دقائق**.
- التأكد أن **Health Check** في Railway مضبوط على `/ping` مع timeout كافٍ (مثلاً 10s).
- إن كانت الخدمة تحت خطة تسمح بذلك: تعطيل **Sleep/Scale to zero** إن وُجد حتى تبقى الحاوية دافئة.

**النتيجة المتوقعة:** تقليل حدوث الاستيقاظ البارد؛ الطلبات الأولى بعد فترة idle تكون أسرع.

**المرجع:** `docs/RAILWAY-TROUBLESHOOTING.md` — القسم 7 (نوم الخدمة).

## الخطة 3: تحسين الصور (أولوية عالية — جهد متوسط)

**المشكلة:** صور مثل `Subscriptions.jpg`, `Promo Banner.png`, `Game Cards.png` تصل إلى 15–23 ثانية — إما حجم كبير جداً أو شبكة بطيئة بدون CDN.

**الإجراءات (اختر ما يناسبك):**

| الإجراء | الوصف | الجهد |
|---------|--------|-------|
| **ضغط الصور يدوياً أو ببناء** | تقليل أبعاد و/أو جودة (مثلاً 1200px عرض كحد، 80–85% جودة). أدوات: TinyPNG، ImageOptim، أو سكربت بـ Sharp. | متوسط |
| **تحويل إلى WebP** | تقديم نسخ WebP للصور الكبيرة مع fallback (مثلاً `<picture>` أو شرط حسب دعم المتصفح). المشروع يستخدم Sharp — يمكن إضافة مسار مثل `GET /assets/img/:name.webp` يولد من الأصل عند أول طلب ويخزن نسخة. | متوسط–كبير |
| **حد أقصى لحجم الملفات المرفوعة** | موجود (multer) — التأكد أن الصور التي يرفعها البائعون تُضغط أو تُحدد أبعاداً عند الرفع (إن وُجدت معالجة Sharp للصور المرفوعة). | منخفض |
| **CDN للصور** | وضع صور المسارات الثابتة (مثل البانر، الأيقونات) على CDN (Cloudflare، أو S3 + CloudFront إن استخدمت S3). | متوسط |

**النتيجة المتوقعة:** تقليل حجم نقل الصور ووقت تحميلها (هدف: أقل من 2–3 ثوانٍ لأكبر صورة في الصفحة الرئيسية).

### ما تم تنفيذه (الخطة 3)

| البند | التنفيذ |
|--------|----------|
| **ضغط الصور + WebP عند الرفع** | **`lib/image-process.js`**: `processUploadedImage()` — تصغير أبعاد (حد 1920 أو `IMAGE_MAX_WIDTH`)، تحويل إلى WebP (جودة 82 أو `IMAGE_WEBP_QUALITY`)، حذف الأصل. عند فشل WebP: تصغير الأصل إلى حد 1200px وجودة 85% (`IMAGE_FALLBACK_MAX`). يُستخدم في منتجات البائع/الأدمن، شعار/بانر البائع، ورفع إعدادات الأدمن (theme). |
| **توليد WebP عند الطلب** | مسار **`GET /assets/img/:name.webp`** يبحث عن الأصل (jpg/jpeg/png/gif) في `client/assets/img`، يولد نسخة WebP ويخزنها في `client/assets/img/.webp-cache/`، ويُرجع الصورة مع `Cache-Control: public, max-age=604800` في الإنتاج. الواجهة يمكنها طلب نفس الاسم بامتداد `.webp` أو استخدام `<picture><source type="image/webp" src="...webp">...</picture>`. |
| **حد حجم المرفوعات** | multer يطبّق `UPLOAD_MAX_FILE_SIZE` (افتراضي 10 MB). المعالجة بعد الرفع تضغط الصورة فعلياً فالحجم المخزَن أصغر. |
| **سكربت ضغط الصور (بناء)** | **`scripts/optimize-images.js`**: يمر على `client/assets/img` (واختيارياً `dist/assets/img` مع `--dist`)، يضغط كل jpg/png أكبر من 50 KB إلى حد 1200px وجودة 85%. مع **`--webp`** ينشئ نسخاً `.webp` بجانب كل صورة. الأوامر: `npm run optimize-images` و `npm run optimize-images:webp`. |
| **CDN (دعم من الواجهة)** | **`/api/config`** يرجِع حقل **`assetBaseUrl`** من `ASSET_BASE_URL` أو `IMAGE_CDN_URL`. إن ضُبط، الواجهة يمكنها استخدامه كأساس لمسارات الصور (مثلاً `assetBaseUrl + '/assets/img/foo.webp'`). |

متغيرات بيئة اختيارية: `IMAGE_MAX_WIDTH`, `IMAGE_MAX_HEIGHT`, `IMAGE_WEBP_QUALITY`, `IMAGE_FALLBACK_MAX`, `OPTIMIZE_IMAGE_MAX_WIDTH` (للسكربت)، `ASSET_BASE_URL` أو `IMAGE_CDN_URL`.

## الخطة 4: تقليل طلبات API المكررة (أولوية متوسطة — جهد متوسط)

**المشكلة:** في نفس الجلسة تُستدعى عدة مرات: `/api/config` و`/api/client/me` — كل استدعاء 150–300ms.

**الإجراء:**
- في الواجهة الأمامية (صفحة رئيسية، layout مشترك):
  - **تخزين مؤقت في الذاكرة (في الصفحة)** لنتيجة `GET /api/config` (لا يتغير خلال الجلسة عادة).
  - **استدعاء `/api/client/me` مرة واحدة** عند تحميل التطبيق ثم تمرير الحالة (loggedIn, user) للمكونات بدل طلبها من كل مكون.
- استخدام **ETag/304** موجودة — التأكد أن الطلبات التالية ترسل `If-None-Match` (العميل لا يعطل الـ cache).

**النتيجة المتوقعة:** تقليل عدد الطلبات في أول تحميل وتحسين LCP ووقت التفاعل.

### ما تم تنفيذه (الخطة 4)

| البند | التنفيذ |
|--------|----------|
| **تخزين config في الذاكرة** | **`client/assets/js/api-cache.js`**: `Key2lixApi.getConfig()` — يُرجع Promise، ويُخزّن النتيجة في الذاكرة حتى إعادة تحميل الصفحة. |
| **استدعاء client/me مرة واحدة** | `Key2lixApi.getClientMe()` — يُخزّن النتيجة في الذاكرة. `invalidateClientMe()` يُبطّل الكاش (يُستدعى بعد تسجيل الدخول/الخروج). |
| **استخدام الكاش في الواجهة** | common.js، form.js، wishlist.js، index.html، client-account، product.html، ai-chat.js، push-subscribe.js، vendor-register، vendor-login، how-to-sell، support، admin، vendor — جميعها تستخدم `Key2lixApi.getConfig()` أو `getClientMe()` عند توفره. |
| **إبطال عند الدخول/الخروج** | client-login: `invalidateClientMe()` بعد نجاح تسجيل الدخول. common.js: `invalidateClientMe()` عند النقر على تسجيل الخروج. |
| **ETag/304 لـ /api/config** | الخادم يضبط `ETag` (MD5 من الجسم) و`Cache-Control: private, max-age=60, must-revalidate`. عند `If-None-Match` مطابق يُرجع 304. |

تم إضافة `api-cache.js` قبل `common.js` في الصفحات التي تستخدمه، وتضمينه في Service Worker للكاش.

## الخطة 5: Cache-Control و ETag للأصول (أولوية متوسطة — جهد قليل)

**الحالة الحالية:** المشروع يضبط `Cache-Control: public, max-age=604800` لـ `/assets/img`, `/assets/css`, `/assets/js` في الإنتاج، و`express.static` مع `etag: true`, `lastModified: true`, `maxAge: 1d`.

**تحسينات مقترحة:**
- التأكد أن **كل** طلبات `/assets/*` تمر من المسار الذي يطبّق الـ Cache-Control الطويل (الخطة 1 تساعد).
- إن أضفت **أسماء ملفات مُهاشة** عند البناء (مثل `home.a1b2c3.css`) أضف **`immutable`** لرأس Cache-Control لهذه الملفات لتجنب إعادة التحقق.

**النتيجة المتوقعة:** إعادة الزيارة تعتمد على الكاش وتقليل 304 المتكرر غير الضروري.

## الخطة 6: CDN أمام التطبيق (أولوية متوسطة — جهد حسب البنية)

**المشكلة:** كل الطلبات (صفحات، API، أصول) تمر عبر نفس المنفذ والنطاق → زمن استجابة وانتظار أعلى تحت الحمل.

**الإجراء:**
- وضع **Cloudflare** (أو مزود مشابه) أمام النطاق:
  - **Cache** مسارات الأصول فقط: قواعد Page Rules أو Cache Rules لـ `*keylix.com/assets/*` → cache لمدة أسبوع.
  - **عدم تخزين** مسارات الـ API ومسارات الجلسة (مثل `/api/*`, `/vendor-login`, `/client-account`) أو تخزين 0.
- التأكد أن **SSL/TLS** Full (strict) إن كان التطبيق يخدم HTTPS.

**النتيجة المتوقعة:** تحميل CSS/JS/صور من أقرب edge للمستخدم وتقليل الحمل على السيرفر.

---

## الخطة 7: تحميل JS غير حرج (Lazy load) (أولوية منخفضة — جهد متوسط)

**المشكلة:** ملفات مثل `search.js`, `ai-chat.js` قد لا تكون ضرورية فور تحميل الصفحة.

**الإجراء:**
- تحميل سكربتات **غير حرجة** بشكل **مؤجل**: `defer` أو `async` أو ديناميكي عند الحاجة (مثلاً عند فتح البحث أو نافذة الدردشة).
- ترتيب السكربتات: الحرجة أولاً (مثلاً common.js، lang.js)، ثم الباقي مؤجل.

**النتيجة المتوقعة:** تحسين First Contentful Paint وTime to Interactive.

---

## الخطة 8: مراقبة وحجم الملفات (أولوية صيانة)

**الإجراء:**
- تشغيل أداة **Lighthouse** (أو WebPageTest) على الصفحة الرئيسية وتسجيل LCP، TBT، حجم أكبر الموارد.
- إن وُجد سكربت بناء: إضافة خطوة تُخرج **قائمة بأكبر الملفات** في `client/assets` (مثلاً أعلى 20 ملفاً بالبايت) لمراجعة دورية.

**النتيجة:** تحديد أي أصول ما زالت ثقيلة وتستحق تحسيناً أو نقلها لـ CDN.

## ملاحظات إضافية

- **طلبات 206 (Partial Content):** إن كانت الصور تُطلب بـ Range وترد 206، تأكد أن الخادم يدعم Range بشكل صحيح وأن العميل لا يعيد طلب الملف كاملاً عند كل تحميل. `express.static` يدعم Range افتراضياً.
- **wp-admin/wordpress:** الرد 404 سريع (~293ms) مناسب؛ لا حاجة لتغيير.
- بعد تطبيق الخطط 1 و2 و3 يُفترض أن تلاحظ تحسناً واضحاً في زمن التحميل الأول وأثناء التصفح؛ يمكن بعدها قياس النتائج وتوثيقها في هذا الملف أو في تقرير أداء منفصل.

إذا رغبت، يمكن البدء بكتابة التعديلات الفعلية في `server.js` للخطة 1 (تقديم `/assets` مبكراً) وخطوات UptimeRobot للخطة 2.
