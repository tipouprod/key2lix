# تشخيص احترافي لمشكلة تسجيل الدخول

عند فشل تسجيل الدخول على الموقع المنشور (مثلاً Railway)، اتبع الخطوات التالية بالترتيب واستخدم السجلات وواجهات التشخيص المدمجة.

---

## 1. التأكد أن طلب الدخول يصل للسيرفر

في **سجلات Railway (Logs)** ابحث عن أحد الأنماط التالية بعد محاولة تسجيل الدخول:

| ما تبحث عنه | المعنى |
|-------------|--------|
| `"method":"POST","url":"/client-login"` | طلب النموذج وصل للسيرفر. تابع الخطوة 2. |
| لا يظهر أي POST /client-login | الطلب لا يصل (شبكة، وكيل، مهلة من المتصفح). راجع: كاش المتصفح، إعادة تحميل قوية لصفحة الدخول، تجربة من متصفح/جهاز آخر. |

---

## 2. تحليل توقيت معالجة الدخول (Form Login)

عند وصول POST /client-login، يُسجّل السيرفر سطراً من نوع **`client/login/form`** مع تفاصيل التوقيت. ابحث في السجلات عن:

```
client/login/form
```

في الـ **Attributes** (أو الحقول المسجّلة) ستجد مثلاً:

| الحقل | المعنى |
|-------|--------|
| **loginId** | معرف الطلب (لمتابعة نفس المحاولة في السجلات). |
| **step** | المرحلة: `ok` = نجاح، `invalid` = بيانات خاطئة، `save_failed` = فشل حفظ الجلسة، `rate_limit` = تجاوز المحاولات، `missing` = بريد/كلمة مرور ناقصة، `error` = استثناء. |
| **ms** | الوقت الكلي من بداية المعالجة حتى نهاية هذه المرحلة (بالميلي ثانية). |
| **validateMs** | وقت التحقق (بريد، كلمة مرور، DB). |
| **saveMs** | وقت حفظ الجلسة في DB. |

**كيف تستخدمها:**

- إذا **ms** كبير (مثلاً > 5000) والبطء في **saveMs** → جدول الجلسات أو SQLite بطيء/مقفل؛ راجع الخطوة 3.
- إذا **step: save_failed** → راجع رسالة **err** في نفس السطر؛ غالباً قفل SQLite أو خطأ في الكتابة.
- إذا **step: ok** لكن المستخدم لا يرى أنه دخل → المشكلة بعد الرد (كوكي لا يُرسَل أو صفحة التوجيه)، راجع الخطوة 4.

---

## 3. فحص استجابة جدول الجلسات (Session DB)

افتح في المتصفح (على نفس النطاق، مثلاً https://key2lix.com):

```
https://key2lix.com/api/client/login-diagnostic
```

ستحصل على JSON يشمل:

| الحقل | المعنى |
|-------|--------|
| **env** | بيئة التشغيل (يفترض `production` على Railway). |
| **sessionStore** | `db` أو `memory`. |
| **sessionDbPingMs** | وقت قراءة واحدة من جدول الجلسات (ميلي ثانية). إذا كان مرتفعاً (> 500 أو آلاف) فقاعدة البيانات أو القرص بطيء. |
| **sessionDbPingError** | إن وُجد، معناه خطأ عند القراءة (مثلاً قفل أو انقطاع). |
| **hasCookie** | هل الطلب الحالي أُرسل مع كوكي الجلسة. للتشخيص غالباً ستكون `false` إن فتحت الرابط بدون تسجيل دخول. |
| **host**, **protocol** | للتأكد من النطاق وبروتوكول الطلب. |

**كيف تستخدمها:**

- **sessionDbPingMs** مرتفع جداً → ضغط على SQLite أو قرص بطيء؛ قلل الطلبات الثقيلة أو انقل الجلسات لـ Redis لاحقاً.
- **sessionDbPingError** موجود → راجع السجلات لتفاصيل الخطأ وأسباب القفل/الانقطاع.

---

## 4. التحقق من الجلسة بعد الدخول

بعد نجاح تسجيل الدخول (redirect 303 إلى /client-account):

- في السجلات، إذا ظهر **`client/me: no session`** للطلبات التالية (مثل GET /api/client/me أو GET /client-account) → المتصفح لا يرسل الكوكي أو الجلسة لم تُحفظ.
- راجع [LOCALHOST-WORKS-RAILWAY-DOESNT](LOCALHOST-WORKS-RAILWAY-DOESNT.md): **COOKIE_DOMAIN**، **NODE_ENV=production**، **SESSION_STORE=db**، وافتح الموقع دائماً عبر **https://**.
- استخدم **/api/session-check** للتأكد من إعدادات الجلسة (env، sessionStore، trustProxy، cookieDomainSet).

---

## 5. ملخص سريع

1. **سجلات Railway:** ابحث عن `POST /client-login` و `client/login/form` — تأكد وصول الطلب ومرحلة التوقيت (step, ms, saveMs).
2. **/api/client/login-diagnostic:** تحقق من sessionDbPingMs ووجود أخطاء في قراءة الجلسات.
3. **/api/session-check:** تحقق من env و sessionStore و trustProxy.
4. إن **step: ok** لكن الصفحة لا تعرض المستخدم مسجلاً → راجع الكوكي والنطاق (COOKIE_DOMAIN، https، نفس النطاق).

للتفاصيل العامة عن النشر والجلسات راجع [RAILWAY-TROUBLESHOOTING](RAILWAY-TROUBLESHOOTING.md).
